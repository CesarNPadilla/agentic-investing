# Runtime process and environment preparation

The private-file boundary is complete in its scoped four-file test. The next combined fixture tests two distinct remaining boundaries: the launched child's environment and its ability to acquire sensitive handles to the elevated owner's currently running PowerShell process.

`workers/paper_runtime_environment.py` constructs a complete replacement block from controller-selected absolute local Windows paths. It never copies the parent environment. It supplies explicit Windows executable paths, executable extensions, PowerShell module path, application home/temp paths and Python user-site/safe-path settings. Unsafe relative/network paths, delimiters, expansion syntax, alternate streams, parent traversal and temporary paths outside the configured home are rejected. Path format/containment does not qualify real identity, profile registration, existence, ACLs, executable integrity, Windows module-path expansion or trusted controller configuration. The helper is not integrated into any active trading runner.

Fifteen tests include malicious path/temp cases, synthetic broker-secret/Python/proxy exclusions, an actual isolated Python child and an actual same-owner .NET PowerShell child with the replacement block. PowerShell startup supplies its own module-path defaults; these observations do not qualify a deployed import/search path. Parent markers are dummy values; no real credentials are inspected.

The owner-run fixture creates an isolated diagnostic application home/temp directory under Logs, without loading the Windows user profile. It clears ProcessStartInfo.EnvironmentVariables before assigning the tested block, redirects stdin/stdout/stderr, closes child stdin, and starts a hidden credentialed runtime process. The local SecureString password is passed directly to ProcessStartInfo.Password. It is not printed, written to a file or sent to the agent. The child counts unexpected/missing environment names without returning values and verifies a synthetic owner-session marker is absent.

Seven sensitive owner-process handles must be denied: VM_READ, VM_WRITE, VM_OPERATION, CREATE_THREAD, DUP_HANDLE, WRITE_DAC and WRITE_OWNER. Granted handles are immediately closed; no process memory is read or written, handles duplicated, threads created, tokens opened or broker called. An own-process VM_READ grant is the positive control. Invalid PID/error codes never count as access denied. Nine native regression tests parse/compile the exact helper, demonstrate all seven own-process grants and distinguish an invalid PID from denial. They do not qualify the actual runtime/owner pair.

The wrapper requires a disabled distinct runtime and protected administrator-owned diagnostic layout; it captures a zero exit and empty stderr, verifies code hash and exact result inventory, disables the account in cleanup, then exclusively writes the acceptance report in Receipts. A failure produces no passing receipt and retains diagnostics. Host/parent termination can interrupt cleanup; no service watchdog or crash cleanup is qualified. The owner wrapper process remains alive throughout the test, so its PID cannot be recycled during a completed check.
