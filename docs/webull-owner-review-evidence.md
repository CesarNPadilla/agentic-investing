# Webull owner-review signature and retention

The staged verifier and journal implement review evidence only. They do not approve a loss-stop reset, connect to a broker, deploy a service or enable the trial. All new tests use generated synthetic credentials, signed assertions and disposable databases; no actual owner credential or password was used.

`security/webull_review_signature.py` verifies an actual WebAuthn signature against a controller-selected credential and exact review envelope. The signed challenge binds the review-only action, UUID, account, prerequisite-review digest, credential digest and issue/expiry window, with a distinct challenge domain and 32-byte nonce. The prerequisite digest binds the state, policy, reconciliation and calendar through the existing review checker. The window is at most 300 seconds; the expiry boundary is rejected. The verifier requires user presence, user verification, the localhost RP and the staged origin `http://localhost:8767`. No application is listening at that origin. Earlier Alpaca authentication/recovery receipts cannot substitute for this action.

The expected envelope and public credential must come from protected controller state, rather than a runtime-supplied request. Successful cryptographic verification alone does not establish enrollment ownership, Windows Hello use, credential provenance, trusted source qualification or protected deployment. The synthetic prerequisite checker's signature boolean is not replaced or promoted into real authority by this implementation.

`security/webull_review_journal.py` exclusively initializes a database pinned to one exact envelope. Consumption freezes and verifies the original signed receipt inside a SQLite immediate transaction; a caller's claimed verification result is insufficient. It stores the original receipt, its digest and the verifier-supplied consumption time. Reopening and concurrent duplicates cannot consume that review again. Rejected input leaves the review unused. Historical verification checks the retained signature at its original consumption time, rather than treating an old receipt as a fresh approval. Missing databases are not recreated by verification or consumption.

The output distinguishes `review_evidence_consumed=true` from `approval_consumed=false`. Reset, execution and trial flags remain false. One journal is scoped to one review, not a mutable risk ledger or a reusable authority service. Its hashes detect checked content changes; they do not supply an independent integrity anchor. Deleting a consumed row or restoring an earlier valid database can defeat its replay history. Deployment must protect the database, trusted envelope, credential and recovery anchor before these controls qualify for actual authority. Authenticator enrollment/counter policy, server challenge issuance, application lifecycle and atomic reset-state integration also remain pending.

Verification batch: signature tests 18/18, journal tests 10/10, total 28/28 (100%). Cases include altered account/plan/receipt, forged verification, wrong credential/origin, missing presence/verification, freshness boundaries, malformed nonce, invalid signature, restart/concurrency replay, changed context, retained evidence corruption and missing database. The broader selected regression count and exact source digests are recorded in [the qualification record](examples/webull-sandbox/owner-review-evidence-qualification.json).

The separate staged `security/webull_owner_review_app.py` supplies the concrete review-only interface. It requires three distinct paths outside the repository: an already selected public credential record, the exact controller-prepared envelope and an exclusively initialized review journal. It never enrolls/replaces a credential or initializes missing state. Host/origin checks, strict HTTP-only challenge cookies, no-store/frame protections, at most eight pending 120-second challenges, a streamed 65,536-byte assertion bound and consume-on-attempt challenges protect the review flow. Changed in-flight context blocks. The journal re-verifies the original assertion before durable retention. The CLI binds only 127.0.0.1:8767 with proxy headers disabled; it has not been launched or installed.

Seven application tests cover complete synthetic signing, changed display/in-flight context, forged assertions, duplicate completion, local host/origin/cookie/header controls, challenge expiry/throttling, oversized input, missing journal and colliding private paths. The combined signature/journal/application implementation batch is now 35/35 (100%). Browser Windows Hello behavior and the actual owner ceremony remain untested; endpoint tests do not establish Windows account separation or ACL protection.

Before an actual owner ceremony, engineering must stage and verify immutable controller code, private state ownership/ACLs, the controller-selected public credential and an understandable source-qualified review package; provision independently protected replay recovery; and bind the actual owner process lifecycle. A runnable development module is not this deployed package. The app displays account/plan digests for comparison with that separate owner review. No actual envelope or real review journal was created during this implementation, and no signature is requested for a synthetic plan.

Trial launch remains 0%, forward evidence 0/60 and overall Webull readiness is not numerically established. The required external action remains [Webull's technical answers](webull-provider-evidence-questions.md). Actual owner authentication and protected provisioning will require direct owner participation when their concrete deployment package is ready. No new password fixture is requested by this stage.
