# Phase v1.1c — atomic synthetic reservation lifecycle

**FOUNDATION COMPLETE / FULL v1.1 INCOMPLETE.** The independent approved reservation workstream now has a dedicated synthetic ledger. See [current implementation status](examples/risk-policy-v11c/implementation-status.json). This is SQLite lifecycle qualification, not completion of the approved PostgreSQL serializable design.

The ledger reserves one conservative acquisition-cost amount including fees against two separately initialized fixed budgets: settled cash and sleeve capacity. Both must have room. One explicit synthetic scope is supported; no account/symbol inventory or marked portfolio risk is modeled. Proposal identity and a SHA-256 digest bind the reservation; exact duplicates are idempotent and changed reuse rejects. Transactions serialize replay/check/append, so concurrent proposals cannot oversubscribe either budget.

Partial fills retain the original commitment while open: filled cost becomes consumed capacity and unfilled commitment remains reserved. UNKNOWN, PENDING_CANCEL and unverified terminal reports do not release capacity. Explicitly verified synthetic CANCELED/REJECTED/FILLED evidence releases only the unfilled amount; acquisition costs remain consumed. Terminal retries are idempotent for matching filled amount; terminal proposals cannot reopen or reserve again. Fill regression, nonfinite values, over-budget fills and unknown proposal IDs reject without changing capacity. Status verification is a fixture assertion, not authenticated brokerage evidence.

Initialization refuses existing database tables. Missing state is never recreated on open. Replay verifies event ordering, hash links, valid lifecycle and budgets; corrupt/missing persistence fails closed. Failed append rolls back. Connections close after each transaction. The journal is separate from v1.1b's latch store and all application databases; it has no API/broker/scheduler integration and cannot authorize execution. Atomic integration of latch, risk evaluation and reservations remains outstanding.

Validation: **22 new tests**, **190 targeted tests passed** total. Coverage includes independent cash/sleeve rejection, exact-capacity concurrent contention, exactly-once duplicate reservation, partial-fill restart, verified/unverified terminal evidence, cancellation/unknown status holds, cumulative fill validation, idempotency, corruption/missing state and rollback. Static checks, schemas, source digests and git diff --check pass.

Limits: fixed synthetic acquisition-cost budgets, no dynamic balance/valuation/replenishment or multi-account/symbol risk; no sales capacity release; no PostgreSQL concurrency qualification. Hash links lack an external trust anchor, so full rewrite or valid suffix truncation is not detectable. Replay scans the entire ledger. Bootstrap amounts and terminal verification do not confirm actual funds or actual orders.

Runtime policy still needs concrete whole-account limits, portfolio exposure rules, trusted sources, operational owners, baseline/reset rules and qualified funding/environment evidence. No missing choices were invented.
