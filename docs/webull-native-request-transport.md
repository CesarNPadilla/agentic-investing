# Webull native diagnostic request transport

The staged Python `LocalRequestPipe` creates a single-use Windows named pipe with a protected explicit DACL: the actual owner process SID receives control and the distinct runtime SID receives only data read/write, ReadAttributes and synchronization rights. The process identity must match the configured owner. The pipe requests first-instance protection and PIPE_REJECT_REMOTE_CLIENTS, sets a medium mandatory label and reads the label back. It also reads back the owner and protected DACL and refuses a mismatch before accepting requests. No global privileges, deployment-directory ACLs, broker credentials or execution flags are modified.

Connection and reads use overlapped Windows I/O with a shared positive deadline of at most five seconds. Pending operations are cancelled and drained before releasing their buffers/events. If cancellation cannot complete within a one-second grace, the dedicated process terminates instead of releasing memory still referenced by I/O. The framing is a four-byte unsigned big-endian size followed by 1–4096 bytes of JSON; partial input, excessive length and invalid requests never reach registration. One request is processed per connection, which is closed on success or failure. Further frames on that connection are not processed.

After the complete frame is read, the existing native identity helper reads that connection's client token and restores the server identity. The configured owner/runtime scope is checked before journal registration. Neither role receives owner approval, reset or broker authority. The five-second transport deadline does not cover SQLite registration or qualify the trading monitor's hard timer, a persistent service watchdog or complete controller latency.

Ten actual local same-user native transport tests cover fragmented valid input, empty/oversized lengths, missing-client cancellation, incomplete-body deadlines, forbidden JSON and duplicate request rejection across connections, exact owner/runtime DACL readback, rejection and cleanup on a permissions mismatch, and first-instance rejection of an existing pipe name followed by reuse after closure. They use disposable synthetic journals and hidden local clients. These tests do not qualify the actual runtime account or remote-host rejection. The latter is configured using the documented native flag, but no remote host was used to demonstrate denial.

The owner-run [native cross-account fixture](../scripts/test_paper_runtime_native_pipe.ps1) has passed in its synthetic scope. It launches the server under the elevated owner identity and a dummy .NET client as AgenticPaperRuntime, with the locally entered password. A new synthetic journal is exclusively created in RiskState; startup/result evidence is written in Receipts, outside runtime write authority. Startup publication and the owner's gate are atomic. The server obtains runtime identity from the native client token, registers one synthetic review request and grants no admission. The wrapper checks result identity, request ID, journal count, zero exit codes and disabled authority flags, then disables the account. It installs no service and adopts no real risk state. Parent termination/host crash can interrupt wrapper cleanup; this fixture is not a supervised deployed runtime.

The October 8 runtime fixture was independently verified against its retained result, protected synthetic journal, startup gate, exact retained client source and empty server/client stderr. The registered caller identity hash matches the local runtime account; one synthetic request is retained and all admission, approval, reset and execution flags remain false. The account is disabled again. The owner wrapper reported successful zero-exit checks, but process exit codes are not persisted in the result itself. See the [verification record](examples/webull-sandbox/runtime-native-pipe-verification.json). Do not repeat the completed fixture.
