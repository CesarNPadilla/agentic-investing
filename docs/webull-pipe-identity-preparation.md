# Webull pipe identity and journal bridge preparation

The staged native Windows helper identifies the client associated with the last message read from a connected server-side pipe handle. It uses the client thread token, rejects failed impersonation and anonymous identity, and restores the server identity before returning. Reversion failure terminates the dedicated controller process. It does not use a username, SID or authentication flag from runtime JSON. The [Microsoft impersonation contract](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-impersonatenamedpipeclient) ties identity to the last message read and requires failure checks; [reversion guidance](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-reverttoself) requires process shutdown on reversion failure.

Four failure-path tests and a real disposable local same-user pipe test pass. The actual client requests identification-level security, writes a dummy message, and the server reads the token then verifies there is no residual thread impersonation. This tests the native identity helper, not runtime-account isolation or a deployed controller. No credentials, approvals or broker calls are used.

The staged registration bridge permits requests only from distinct configured owner/runtime SIDs supplied by trusted controller configuration. Persistence occurs after identity restoration. A private caller-identity digest is retained atomically with request registration; no raw SID is emitted in public receipts. Both roles may request a review, but neither receives approval/reset/order authority. Five bridge tests cover both roles, unknown callers, failed identity lookup, replay and identical-role configuration refusal. The bridge depends on the future transport supplying the bytes just read from that same handle; it does not create or qualify the transport itself.
