# Phase v1.1b — synthetic persistence and sticky latch foundation

**FOUNDATION COMPLETE / FULL v1.1 INCOMPLETE.** The approved independent implementation scope now has a durable isolated synthetic journal around the v1.1a sleeve diagnostic. See [current implementation status](examples/risk-policy-v11b/implementation-status.json). Earlier snapshots remain unchanged historical evidence.

Explicit initialization creates a separate SQLite journal and refuses a database containing any existing tables. Opening missing state never recreates it. Initialization starts latched by default; explicitly unlatched bootstrap is a synthetic fixture option only. The store verifies prior records and replay, merges persisted latch state into caller inputs, evaluates approved sleeve checks and appends the resulting evidence within a single serialized write transaction. Caller input cannot clear a persisted latch. Daily/cumulative loss or manual synthetic latch remains sticky across restart and recovered P&L. No reset API is provided because operational reset ownership and complete baseline/session rules remain unspecified.

Missing/corrupt state, inconsistent replay and failed persistence raise a blocking error; no successful diagnostic is returned. Concurrent appends serialize without dropping events. The store closes connections and refuses databases containing other tables. It is not wired to the API, existing trading service, portfolio database, broker or scheduler. All diagnostic outputs keep execution unavailable and whole-account qualification false.

Validation: **12 new persistence tests**, plus previous sleeve/policy/risk tests, **168 passed**. Tests cover loss/manual latch persistence, restart and caller-clear resistance, default latch, missing state, existing database refusal, invalid bootstrap, journal tampering, concurrent writes and rollback after append failure. Static checks, source digests, JSON parsing and git diff --check pass.

Limits: this is dedicated local SQLite synthetic persistence, not qualified PostgreSQL cash/sleeve reservations. Hash-linked records detect inconsistent changes but have no external trust anchor; complete malicious rewrites or valid suffix truncation are not detectable. The journal replays all records and makes no production scale or immutable audit guarantee. Actual operational reset, timezone-bound daily baseline creation, deposit-safe cumulative baseline management and broker-order recovery are not implemented.

Next independent foundation: atomic reservation design and synthetic lifecycle tests, followed by PostgreSQL-specific qualification. Still required for affected runtime branches: concrete whole-account loss and portfolio exposure rules, named trusted quote/snapshot/calendar sources and human owners, complete outage/recovery semantics, verified funding and environment qualification.
